# Fix live testnet execution + apply exchange-mechanics knowledge to the engine

## What the logs actually show

Two separate failures, neither of them a strategy problem:

1. **Bybit: "testnet credentials are not configured."** The Bybit trading code reads two saved values (`BYBIT_TESTNET_API_KEY`, `BYBIT_TESTNET_SECRET`). Only the **Binance** pair is saved on this project — the Bybit pair was never added. The "API key: saved (64 chars)" line in the header is reporting the Binance key, not Bybit.
2. **Binance: `403 ... Generated by cloudfront`.** This is not an auth or signature error and no key change fixes it. Binance's testnet CDN is refusing requests coming from the app's server region outright — the request never reaches the trading API.

Consequence: every high-confidence signal fires an order attempt, fails, and writes an `ERR` line — dozens per minute of pure noise.

## Plan

### 1. Stop the error storm (do this regardless of exchange)
- Before any live order is attempted, check live readiness once (credentials present + a successful account probe). If the selected exchange isn't ready, keep the engine in paper mode and show a single persistent banner instead of one error row per signal.
- Add a circuit breaker: after 3 consecutive live-order failures, auto-disable live mode, surface one clear reason, and require an explicit re-arm click.
- Collapse repeated identical errors in the feed into one row with a count.

### 2. Make Bybit the live venue
- Bybit testnet is reachable from the server (unlike Binance's CloudFront-blocked testnet), so it becomes the default live provider.
- Request the Bybit testnet key/secret so the existing Bybit V5 code path can authenticate.
- On save, run a status probe (wallet balance) and show a green "live armed" state with the account equity, so readiness is proven before any order is sent.

### 3. Demote Binance to paper-only with an honest message
- Keep the Binance code, but when the status probe returns the CloudFront 403, label it "blocked at network level from this region — not a key problem" rather than the generic testnet-failure text, and grey out the Binance live toggle instead of letting it spam errors.

### 4. Use the exchange-mechanics knowledge to actually improve the engine
The Bybit perpetual mechanics already modelled in paper mode (0.055% taker per leg, 8h funding at 00/08/16 UTC, mark-price liquidation, tiered maintenance margin, book-walk slippage) are currently only used to *score* trades after the fact. Turn them into pre-trade gates on both paper and live paths:

- **Funding-aware entry**: block or shrink positions opened within ~10 minutes of a funding stamp when the funding rate is against the intended direction and would exceed the expected edge; prefer the side that *collects* funding when the signal is otherwise a coin-flip.
- **Cost hurdle before order, not after**: require the signal's expected move to clear `round-trip fee + measured slippage + spread + expected funding carry` with the learned margin. Signals that don't clear it never become orders — that removes the biggest source of negative net expectancy.
- **Risk-limit-aware sizing**: cap notional at the tier where maintenance margin jumps, and refuse any size whose liquidation price sits inside normal volatility for that symbol's regime.
- **Order type by spread**: when spread is wide, use a post-only limit at the touch with a timeout-to-cancel instead of a taker market order, cutting the fee from 0.055% to the maker rate and removing the spread cross.
- **Live/paper parity check**: mirror every live order into the paper ledger and report the realised difference (live fill vs simulated fill) per symbol, so the microstructure model is continuously calibrated against real fills instead of assumed ones.

### 5. Live risk rails
- Hard caps applied server-side, not in the browser: max concurrent live positions, max notional per symbol, daily loss limit that halts live mode, and a kill switch in the header.
